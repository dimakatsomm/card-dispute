# Review 01 — Architecture, data model, dispute rules, M1 decomposition

Reviewer stance: adversarial. Tags: [verified] = checked on a primary source this session; [recall] = memory; [guess]. Canary facts K1-K3 not disputed. I verified only two things on primary sources (Service Connect mechanics; PG reserved words). Everything else is reading the docs or recall.

## 1. Fatal flaws (change before code is written)

**F1. A resolved-ACCEPTED (or REJECTED) transaction can be disputed again, so a customer can be refunded twice.** [verified by reading 04 + 03] The only guard is the partial unique index on `status in (SUBMITTED, UNDER_REVIEW)`. Once the first dispute is RESOLVED_ACCEPTED it is no longer "active", so a second POST passes eligibility rule 7, and auto-rules can ACCEPT it again (<= R200, non-FRAUD). 04 contradicts itself: "resolved or withdrawn may be disputed again" vs. Q-07 default "only if previous was WITHDRAWN". S-02 does not encode either. Money bug on the thing the product exists to protect. Fix: add eligibility rule "no prior RESOLVED_ACCEPTED dispute on the transaction (and a cap on re-opens after WITHDRAWN/REJECTED)", with a DB-level backstop. Pick the Q-07 answer now, not later.

**F2. Auto-resolution decides on a stale snapshot (TOCTOU) and the internal API has no precondition.** [verified by reading] `dispute-auto-rules` decides from the `DisputeCreated` payload (reasonCode, disputedAmount). The relay runs once per minute, so the window is 60s or more. The user may `EDIT` (SUBMITTED only) amount/reason in that window: create R150/OTHER, edit to R4,000, the Lambda still sees R150 and ACCEPTs the R4,000 dispute. `PUT /internal/dispute/{id}/resolution` takes no `If-Match`/expected version, and `autoDecide` is never told to re-read current state. The same gap hits WITHDRAW vs RESOLVE (see F). Fix: internal resolve/review must carry `expectedVersion` (or disputes re-evaluates server-side under `SELECT … FOR UPDATE`), and a version mismatch means "re-decide", not "apply".

**F3. Lambdas cannot reach the ECS Service Connect endpoints the design relies on.** [verified: AWS docs say Service Connect works by a proxy container injected in each ECS task, and "doesn't use or create DNS hosted zones in Route 53"; so a Lambda in the VPC has nothing to resolve `auth`/`users`/`disputes` to. Inference that this means Lambda is excluded: recall, medium-high confidence]. 01 and 05 have notifier, auto-rules and evidence-intake Lambdas calling users/disputes "over Service Connect" and the SG table lists Lambdas as callers. The stated reason for Service Connect ("no internal ALB cost") disappears if an internal ALB/NLB (or Cloud Map DNS-namespace registration done separately) is needed for M2. Decide this before writing `AUTH_URL`/`USERS_URL` config, SGs and S-04's HTTP client. It also changes cost (+$25-30/mo for an internal ALB, [recall]) and where NAT/ENI traffic goes. Also: a Lambda has no warm token cache across cold starts, so each cold container calls `/validate` via the service it hits.

**F4. `/validate` has two contradictory specs and the weakest authN in the system.** The route table in 02 says principal = service, scope `auth/validate`; the note under it says network-only, no token; 05 lists `auth/validate` as a scope; CLAUDE rule 5 says defence in depth. See claim B. Resolve before S-04/A-01.

**F5. The DUPLICATE auto-accept rule cannot be evaluated by the architecture as written.** `autoDecide` needs "another POSTED txn, same card/merchant/amount within 48h" as context. The auto-rules Lambda has only `disputes/resolve`; transactions `GET /transactions` is user-only (T-01 rejects service principals); no s2s transactions route exists, and disputes holds only a snapshot of one txn. So either the rule is dead code or an unspecified route/scope appears in M2. Add the route (and the transactions scope) to 02 and 05 now, or compute the duplicate flag in disputes at create time (when it has the user's token) and store it.

**F6. `users.user` will not create as written.** [verified: `USER` is reserved in PostgreSQL 18; `TRANSACTION`, `KEY`, `VERSION` are non-reserved] D-02 says "user, account, card per docs/03". An unquoted `CREATE TABLE users.user` is a syntax error, and every query then needs quoting. Rename (`app_user`/`customer`) in 03 before D-02. Cheap but it breaks the first migration.

**F7. `auth_identity.user_id` and `user.auth_id` are both NOT NULL logical refs to each other, with no defined writer.** [verified by reading] See claim C. No flow creates a user (sign-up is out of scope), no service may write another schema, and the two uuids must be pre-agreed. As written, only a privileged seed script that bypasses the schema isolation can create a customer. Define the provisioning procedure (who generates the uuids, who writes in what order, what a half-provisioned user looks like) before D-01/D-02.

**F8. Requirement gap: the customer cannot read a dispute.** Charter: customer should "see where the dispute stands". API has only POST/PUT (+POST evidence). There is no `GET /dispute/{transactionId}` or list, and `/me` and `/transactions` do not carry dispute status. Emails are the only status channel. Add the read route(s) and put them in M1's outcome, or change the charter.

## 2. Per-claim verdicts

**A. Central `/validate`: partially disagree. [recall/reading, medium-high]**
- Security value of the central call over local JWKS is nil: auth verifies the same JWT. The only unique value is sub -> userId and ACTIVE/DISABLED status. That can be had by (a) a pre-token-generation Lambda adding `custom:user_id` to access tokens (the verify doc says access-token customisation needs Essentials/Plus, which is the new-pool default; confirm V2 trigger is available in af-south-1 [guess]), or (b) keying ownership on `sub` itself, or (c) local verify plus a cached lookup.
- Costs introduced: auth is a single task (0.25 vCPU) on the critical path of every call, including every Lambda->service call; deploys of auth cause 503 on a cold cache. "Fail closed 503" is the right failure mode but the blast radius is total (no read-only degrade).
- Retry rule conflict: 01 says retries only on idempotent GETs; `/validate` is a POST, so a single network blip = 503; 5 consecutive failures opens the circuit for 30s. Specify that `/validate` is retried (it is safe).
- 60s cache means a DISABLED user or revoked session stays valid up to 60s; local JWT verification never sees Cognito token revocation anyway ([recall]: revocation needs a call to Cognito/userinfo, not signature checks). Document the accepted window.
- Cache is keyed by the bearer token string: bound it (LRU) or an attacker spraying distinct garbage tokens grows memory; "never caches invalid" means each garbage token costs an auth round trip: a cheap amplification path to DoS auth.
- Status split: a user `SUSPENDED/CLOSED` in users still validates ACTIVE in auth_identity (see C).
- I accept the structure only because the owner asked for `POST /validate`. I would still do local verification in auth-client and let `/validate` be the mapping/policy call.

**B. Network-only authN for `/validate`: disagree. [reading; threat reasoning guess, medium]**
- The justification ("returns only claims of a token the caller already holds") is wrong: the response adds `authId`, `userId`, status and the `unknown_subject` reason, none of which are in the token. So a caller can use it as an oracle: sub -> internal userId mapping, whether a sub is provisioned, whether a service client is allowed.
- With code execution in one task (e.g. transactions): it holds that service's DB creds and Cognito client secret (`svc-transactions`), plus network reach to auth. It can (1) call `/validate` freely (DoS, oracle), (2) mint service tokens for the scopes it was granted. Note 05 grants **transactions -> `users/cards.read`**, but transactions never calls `GET /cards` (only disputes does, per 01). That is an unnecessary grant letting a compromised transactions task enumerate cards for any `userId` (the route takes `userId` as a query parameter). Remove it.
- SG "auth <- users/transactions/disputes" is a coarse allow-list, not caller identity. Any process in those SGs, including a sidecar or a debug shell, passes.
- Fix options: services verify service tokens locally (aws-jwt-verify; same lib) and use `/validate` only for the user-mapping; or give auth-client a per-service secret header from Secrets Manager (cheap); or Service Connect TLS with a Private CA (cost unknown, I do not trust my memory of the price, [guess]).
- The 02 table vs note contradiction (F4) means a reviewer cannot tell what A-01 should enforce. Also the OpenAPI task C-04 is told "report contradictions, don't resolve", so the contradiction will just bounce.
- Separately: how does `/validate` decide user vs service? It must map by registered `client_id`, not by "has a `username` claim". Otherwise a user-pool client that is allowed a custom scope could mint a user token carrying `users/cards.read` (user principals are rejected by `requireService`, which is good; just specify it).

**C. `auth_identity.user_id` denormalisation: disagree on current spec; the idea is acceptable. [reading, high]**
- Hidden coupling: yes. It is a cross-schema logical FK in both directions, both NOT NULL, with no FK, no reconciliation job, no owner of writes ("Written once at provisioning" has no provisioner).
- State split: `auth_identity.status ACTIVE|DISABLED` vs `user.status ACTIVE|SUSPENDED|CLOSED`. Nothing syncs them; a CLOSED customer remains `valid:true` for dispute creation. Pick one source of truth for "can this person act".
- Consistency failure modes: a user row without identity gives 401 unknown_subject (fine, but looks like a bug); an identity without a user row yields a valid token whose `userId` has no `GET /me` (404 on login); a mismatched pair silently maps a login to another customer's data. With ownership resting entirely on this one mapping, that last one is the worst bug available in the system and there is no check or test for it.
- Simplest alternative: put `cognito_sub` on `users.user` and drop auth_identity.user_id, or put `user_id` in the token (A).

**D. Ownership via denormalised `transactions.user_id`: partially agree. [reading, medium]**
- Within normal use it is safe: every query is `user_id = principal.userId`, and cardId from another user yields empty. "No issue" on IDOR through filters.
- Gaps: (1) the account/card model is single-owner (`account.user_id`), so joint accounts, authorised users and supplementary cards are impossible. A card reissued to a new holder or an account transferred leaves historical transactions owned by the old user_id. The former holder keeps seeing and disputing them; the new one sees none. That is a policy choice, but it is undocumented. (2) Nothing populates `transactions.user_id` in production: "seeded from users" is a seed script, with no ingestion contract, no reconciliation against users, and nothing proving `card_id` belongs to `user_id`'s account. A wrong `user_id` from ingestion is a cross-customer leak with no detection. (3) Ownership is enforced only by application predicates. Row-level security keyed to a per-request setting would be a cheap second wall for "the one thing it must get right"; not in the docs.
- Doc inconsistency: 01 `evaluateEligibility(txn, card, existingActive, now)` vs S-02 `evaluateEligibility(txn, existingActive, input, now)`. Which is it, and does the card matter (rule 6 says it never does)? If it never matters, why fetch it? (Answer in 04: ownership chain. But the chain is already proven by the transactions call.) The users call adds a failure dependency for no decision. I would drop it from M1.

**E. Outbox + 1/min relay: partially agree. [reading + recall, medium]**
- Latency: up to 60s to publish, then 2 more hops, so about 1-3 minutes from submit to auto-resolution, and the same again to the email. Acceptable for a POC; not for "customer is emailed on every status change" if marketed as near-real-time. "on-demand" invocation in 01 is not specified (who triggers it?). It also widens F2's window.
- `FOR UPDATE SKIP LOCKED` with concurrent Lambda invocations is safe against double-sends and deadlock [recall], but only if the SQS send and the `published_at` update share a transaction. A crash after send and before commit duplicates the message (fine: consumers dedupe on `event_id`), and two relays take disjoint batches, so global ordering is lost. Also EventBridge scheduling can overlap if a run exceeds a minute: set reserved concurrency 1 on the relay.
- Ordering: Created and StatusChanged go to different queues for different consumers, and standard queues are unordered anyway, so the notifier can email "resolved" before "submitted", and a retried/DLQ'd Created can arrive after Resolved. Consumers must be written to be order-independent: notifier sends from event payload plus per-aggregate monotonic `version`/sequence and ignores stale; auto-rules re-reads current state (F2). Events carry no version or sequence today. Add one.
- Poison row: `attempts` exists but no max, no parking state; a row that always fails at the head blocks nothing (SKIP LOCKED) but is retried forever.
- Missing: purge of published outbox rows and processed_event; the DB role the relay uses (D-00 only creates `<svc>_migrator` and `<svc>_app`; a third `disputes_relay` role limited to outbox is needed); a DLQ redrive procedure.
- SQS is encrypted with the `cd-data` CMK, and S3 -> SQS notification needs the CMK key policy to allow `s3.amazonaws.com` [recall, high]; easy to miss in `evidence-bucket`.
- Also: Lambda in the VPC to reach SQS needs NAT (the budget has it) or an SQS endpoint.

**F. Dispute rules: partially disagree; several real issues. [reading, high unless noted]**
- Eligibility order: ACTIVE_DISPUTE_EXISTS is rule 7, evaluated last, but also 409 whereas the others are 422. A client sending an invalid amount on a txn that already has an active dispute gets 422 instead of the more useful 409. Defensible, but state it; S-02 says "first failing in doc order", so that is what you will get.
- Missing rule: prior ACCEPTED dispute (F1). Missing rule: nothing stops WITHDRAW -> re-create -> WITHDRAW loops (each emails); needs a limit.
- 120-day window: "whole UTC days, inclusive" is ambiguous (floor of elapsed time vs calendar-date difference). The tests (120 days ago -> ok; 121 -> outside) happen to pass for both only at exact multiples. Define it: elapsed `floor((now - postedAt)/86400s) <= 120`. Measuring from `posted_at` rather than from the transaction/delivery date is a business choice; for NOT_RECEIVED, card-scheme timeframes generally run from expected delivery [recall, medium]; owner should confirm. `posted_at` is nullable; no CHECK ties POSTED to a non-null `posted_at` (03), so a POSTED row with NULL would crash or bypass rule 4. Customers are in SAST (UTC+2): a customer can see "day 120" and be rejected.
- Currency: the POST body has no `currency`, yet S-02 tests "currency mismatch -> INVALID_AMOUNT". Currency comes from the transaction; either add the field or delete that test. Foreign-currency card transactions (billing vs transaction currency) are unmodelled [guess on how common in this domain].
- Auto-accept threshold R200: reasonCode is user-chosen, so "FRAUD always reviews" is cosmetic; a fraudster picks OTHER or NOT_RECEIVED and gets auto-refunded. There is no velocity or per-customer cap, no cooldown, no per-merchant check, and with F1 the same transaction can be refunded repeatedly. "Never auto-reject" is the right call. But then there is no SLA/escalation for REVIEW disputes sitting forever; no timeout.
- State table vs diagram: consistent, apart from these: (a) "any terminal: any action -> INVALID_TRANSITION" conflicts with "re-applying an applied REVIEW/RESOLVE is a no-op success" (S-02 states both). A retried RESOLVE after commit hits a terminal state, so it must be a no-op *only if the outcome matches*, and an error if it conflicts (ACCEPT arriving at a REJECTED dispute). Spell this out or the Lambda goes to the DLQ on every retry. (b) 02 says PUT with no active dispute -> 404, but P-01 acceptance says "terminal -> 409"; after resolution there is no active dispute, so it is 404. Pick one. (c) 04 says re-opening needs prior WITHDRAWN only; the first sentence says resolved too (F1). (d) EDIT while `UNDER_REVIEW` gives 409 INVALID_TRANSITION; fine.
- Concurrency USER WITHDRAW vs SYSTEM RESOLVE: not handled. `If-Match` protects only user PUTs; the internal route has no version (F2); no `SELECT … FOR UPDATE` or `UPDATE … WHERE status IN (…) AND version = $n` is specified. Loser behaviours are undefined: a resolve that loses to WITHDRAW should be acked as a no-op by the Lambda (not retried to the DLQ), and a withdraw that loses should be 409 with the current state. Neither is in a test.
- Edits overwrite description/amount/reason and the history row only records `from = to = SUBMITTED, note EDIT`: no before/after values. The "every state change is auditable" claim holds for status, not for the content a rule decision was based on. Store the diff in history (jsonb).

**G. Idempotency: partially disagree. [reading, medium-high]**
- In-flight replay: the idempotency row is inserted in the same DB transaction as the dispute, i.e. only at the end, after two upstream HTTP calls (up to 2s each plus retry). Two concurrent same-key requests both see "no row", both do the work; the second blocks on the first's uncommitted unique key, then gets `23505` which is unhandled (500) or, via the partial unique index, `409 ACTIVE_DISPUTE_EXISTS` instead of replaying 201. Specify reserve-first (`INSERT … ON CONFLICT DO NOTHING` an IN_PROGRESS row in its own short transaction, or advisory lock on hash(user,key)), return 409/`Retry-After` for in-flight, and catch 23505 and re-read.
- `request_hash` must include method + path (`transactionId`), not only the body; otherwise the same key and body against two transactions is a "replay" returning the wrong dispute (or 422 spuriously). Say how the body is canonicalised.
- Define which outcomes are stored. 4xx eligibility rejections are time-dependent (window) so caching a 422 for 24h is wrong; 5xx must not be stored. Replay returns the original response including its old `version`/ETag, so a replay after an EDIT yields a stale ETag; document or return current state.
- Only POST dispute is covered. `POST …/evidence` is a create with a 5-item cap and no idempotency; a retry burns the cap and leaves orphan PENDING_UPLOAD rows. Not stated.
- Scope per user: good. 24h TTL, purge job: no task owns the purge. Max key length 64: validate charset too.

**H. Data model: partially disagree. [reading, high]**
Missing constraints/indexes:
- `dispute`: CHECK `disputed_amount > 0 AND <= txn_amount`; CHECK status vs `resolved_at` (set iff RESOLVED_*); CHECK description length; CHECK reason_code, currency; no snapshot of `txn_type`, card `last4`, `card_id` brand; no index for listing by user (`(user_id, created_at desc)`), no `(status)` index for the back-office queue.
- `dispute_evidence(dispute_id)`, `dispute_status_history(dispute_id, id)` indexes absent. `idempotency_key(expires_at)` for the purge. `outbox` lacks a monotonic ordering key or `attempts` cap; partial index on `published_at is null` should include `id` for ordering.
- `transaction`: no natural/processor key unique constraint (ingestion duplicates); no CHECK `status='POSTED' => posted_at is not null`; no `(user_id, transaction_id)` index (the `transactionId` filter) beyond the UQ on transaction_id alone; `mcc char(4)` pads; no `amount` sign semantic for REFUND/FEE beyond `type`.
- Audit fields: `created_by/updated_by` exist only on dispute; others have none. History lacks `correlation_id`, `version`, request source IP, and before/after payload. `updated_at` on an insert-only history table is meaningless.
- Reserved word (F6). The `citext` extension location and schema search_path for each `<svc>_app` role: not said (users_app needs USAGE on the schema holding citext).
- Snapshot columns on dispute: good idea (value at time of dispute) but a snapshot of `txn_amount` is used by the amount CHECK and nothing re-validates against the txn if it is later REVERSED. Reversed/charged-back transactions during a dispute are unmodelled.
- Cross-schema logical refs with no FK: acceptable, but nothing detects orphans. At minimum a nightly reconciliation query/alarm for the three mappings (user<->auth, txn.user_id<->users, dispute.user_id<->txn.user_id).
- Public ids: UUIDv7 leaks creation time in every id [guess on how much that matters]; not an access-control issue because of 404s.
- RLS absent (D).

**I. POC infra: partially agree. [reading + recall, medium]**
- Cost arithmetic reconciles to $205.20 in the doc's own lines [verified by summing]. But inputs are optimistic: Cognito line is "6 clients hourly" yet computed from 4 clients (2,880 = 4 x 720 per verify-claims); at 6 clients it is about $9.85. Secrets Manager is budgeted at 5 secrets, but 05 needs: 4 app DB, 4 migrator, relay, master, 6 Cognito client secrets = about 16 ($6-7). Alarms ($0.10 each), X-Ray, NAT data for ECR pulls/logs/SQS/Lambda egress, and data transfer are excluded.
- False economies: (1) 1 task per service plus 1 NAT plus 1 writer with no reader: the "2 AZ" claim buys nothing; an AZ event takes out NAT (both AZs lose egress, so ECR/Secrets/SQS/Cognito all fail) or the Aurora writer (no reader to fail over to, recovery by rebuild, minutes [recall]). Fine for a POC if called single-AZ in practice; it is described as "2 AZs". (2) Auth as a single 0.25 vCPU task is a hard SPOF for everything (A). (3) 0.5 ACU is about 1 GiB; `max_connections` is derived from memory at that size and is small [recall, low confidence on the number]. Four pooled services plus migrations plus the relay may exhaust it; set pool max explicitly and test. (4) Aurora min 0.5 never pauses, so the $147 figure is not achievable with 24x7 pools; the docs do say that.
- Cognito/JWKS through NAT: fine and cheaper than endpoints (their $172 vs $46 comparison holds on their prices, which I did not re-check). But all tasks and all four Lambdas (VPC-attached) depend on the one NAT for token calls; with `getServiceToken` caching a NAT outage still fails at expiry. Fine for POC, say so.
- Missing infra: no DNS/domain module (Route 53) although the ALB needs an ACM cert and a name, and SES needs domain verification. No module owns it. SES sandbox: 200/day, verified recipients only, per region (their table); seeded `example.com` recipients will fail in the sandbox: use the mailbox simulator or verified addresses, and the prod-access request for af-south-1 has lead time.
- Secrets rotation "enabled for DB creds" has no task; app role rotation needs a custom rotation Lambda, and whether the AWS-provided rotation templates are available in af-south-1 is unknown to me [guess]. Master secret can use RDS-managed rotation [recall].
- Terraform state locking: S3 native lockfile exists in recent Terraform [recall]; "lock" in bootstrap might not need DynamoDB.
- Migrations as "one-off ECS task" before deploy: no expand/contract rule, so a rollback with a destructive migration breaks the old image.

## 3. What's missing

- Customer read API for disputes (F8); evidence confirmation status for the user.
- Provisioning/sign-up flow for a customer across Cognito, auth and users (F7); offboarding (CLOSED users).
- Token revocation story (global sign-out, stolen refresh token): access tokens are valid up to 15 min + cache.
- Rate limiting per user (WAF rate rule is per IP); dispute spam, evidence flood; mail-bombing via withdraw/recreate (each emails).
- Retention/POPIA concerns [recall: SA data-protection law]: description free text may hold PII, stored forever in `dispute`, idempotency `response_body` and S3; no erasure/retention policy; "financial rows never deleted" vs privacy conflict is not addressed. Evidence files are customer documents; virus/malware scanning absent (magic bytes only).
- Back-office authN: `svc-backoffice` is a client_credentials client, i.e. no human identity. Agent-resolved disputes record `AGENT:<id>` with a service principal; who is the agent? Audit of "who resolved" is not provable.
- Dispute SLA/timers for REVIEW; escalation; chargeback to scheme out of scope but the ACCEPTED outcome has no downstream (refund/provisional credit).
- Observability: correlation id on SQS yes; no alarm on outbox lag (oldest unpublished age), no alarm for relay failures; the DLQ alarm exists but no runbook.
- Lambda config: reserved concurrency, timeouts vs SQS visibility (stated 6x, good), batch size.
- DB connection management from Lambdas (relay opens a connection per minute: fine) and RDS Proxy is explicitly out (blocks pause).
- Domain/DNS/ACM (I).
- Deployment ordering/rollback; expand-contract migrations.
- Threat-model gaps: no entry for response forgery of `/validate`, SSRF through none, dependency/supply chain (pnpm 12/vitest 5 versions are very new; I cannot verify them), log injection via correlation id from the client (validate its charset/length).
- Clock: `now()` injected in domain good; `now` skew between disputes tasks and DB for the window; use DB time or one source.

## 4. Where I'd overrule you

1. Drop the `GET /cards` fetch from the create-dispute path in M1 (the card adds nothing to eligibility, rule 6 is "all eligible", ownership is already proven by the transactions call). It removes a service-token hop and a failure mode.
