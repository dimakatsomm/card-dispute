# M6 — Agent evidence viewing (ADR-072): milestone report

**Verdict: MET locally, 2026-11-05.** An integration-verifier ran against a freshly reseeded local stack built from HEAD. The four Lambdas ran as stand-ins serving their real handler bundles, because the sandbox proxy blocks the Lambda base image. The dev rollout (BO-10g) is owner-gated and outside this close; until it ships, dev has no evidence viewing.

## What shipped
An agent opens a dispute and clicks Download on a STORED file. Disputes then:
1. checks the item belongs to the dispute (404 otherwise) and is STORED (409 otherwise);
2. enforces an exact cap of 30 links per agent per 10 minutes (429 with Retry-After otherwise);
3. commits an insert-only `evidence_view` audit row;
4. invokes the `evidence-viewer` Lambda, which mints a 60 s presigned GET.

The link is an attachment named `<evidenceId>.<ext>`, with the declared type and `no-store`. Disputes never reads the bytes, never takes a key from input, and keeps `DenyDisputesTaskDecrypt`. The SPA opens the link in a fresh tab with no opener and no referrer, and never previews the file.

Customer and service access is unchanged: both get 403 on the agent route, and the customer view carries no link. When retention erases a dispute, the sweeper deletes every version of its evidence objects after the erase commits.

## Evidence it works
**Static and unit checks**
- `pnpm install --frozen-lockfile`, lint, `lint:api`, `check:contracts` and frontend `check:api` + build: all clean.
- `pnpm -r typecheck`: 20/21 packages pass. `local/mock-issuer` fails with a pre-existing TS2305, the same on main; CI doesn't typecheck `local/*`.
- Unit and integration tests: **1,584 tests in 18 packages, 0 failures**. Among them: disputes 302, dispute-domain 238, retention-sweeper 36, evidence-viewer 19, frontend 135.

**End-to-end:** `pnpm test:e2e` passed **64/64, twice**: m1 23, m2 19, m5 15, m6 7.

**Walkthrough by hand, as agent Naledi**
- Customer A uploaded a 236 B PDF and it reached STORED in 2 s.
- The download route returned 200 with `no-store`, and the link had `X-Amz-Expires=60`.
- Fetching the link gave `Content-Disposition: attachment; filename="<evidenceId>.pdf"`, `application/pdf` and `no-store`.
- The sha256 of upload and download matched (`37051bfa…4183`).
- Exactly one `evidence_view` row was written, with agent E's id.
- No log line contained `X-Amz-Signature`.
- The customer's `GET /dispute/{tx}` has no link fields.
- Refusals: a customer token on the agent route got 403; a disabled agent and a request with no token got 401; an unknown item got 404.

**Through the SPA (Playwright):** Download opened a new tab with `opener === null`, and the S3 request carried no Referer. The downloaded file was named `<evidenceId>.pdf` and its hash matched.

**Erasure:** the dispute was resolved and backdated 366 days, then the sweeper ran. It returned `{erased: 1, evidenceVersionsDeleted: 1}`. `ListObjectVersions` under the prefix went from 1 to 0. The row became ERASED with `s3_key` null, and a later download got 409.

## Covered by tests, and not
**Covered by executing tests**
- The check order and every status code.
- That a 429 writes no row.
- The exact cap under concurrency: a mutation test proves the lock matters.
- That `Retry-After` is clamped.
- Fail-closed audit, and that the row survives a viewer failure.
- That `agentId` comes only from the token, and that no key is ever sent.
- Strict invoke schemas on both sides.
- The viewer: https rule, host-only signed headers, expiry equal to `X-Amz-Date` + 60, no URL in logs, and a moto round trip.
- The sweeper:
  - pagination and batching;
  - delete markers on a versioned moto bucket;
  - prefix isolation, including a sibling id and a bad-prefix refusal;
  - retry without re-erasing;
  - the retry window.
- `evidence_view`: grants, the trigger and the cross-dispute FK.
- The SPA: popup-blocked, double-click, per-code errors, the scheme check, and no inline rendering.

**Not verified here (environment), all owed to BO-10g in dev**
- Real SigV4 signature and expiry enforcement. moto served a tampered link and a 95 s-old link.
- SSE-KMS decrypt through the viewer role.
- The real IAM `lambda:InvokeFunction` path.
- ARM64 Lambda images on the real RIE.
- Multi-version deletes on the running stack. The local bucket isn't versioned, so this is covered only by the sweeper's own versioned moto test.
- Service images were built locally without `apk upgrade`, because the Alpine CDN is blocked. They are OS-unpatched; rebuild them where Alpine is reachable.

## Deferred, and why
- **BO-10g, dev rollout (owner-gated).** Everything needed to wire the viewer into dev:
  - Viewer function, ECR repo, role (GetObject on `evidence/*`) and the key-policy allow for that role only.
  - Disputes: `lambda:InvokeFunction` on the viewer and `EVIDENCE_VIEWER_FUNCTION`.
  - Sweeper: `s3:DeleteObjectVersion` and prefix-conditioned `s3:ListBucketVersions`, plus `EVIDENCE_BUCKET`.
  - Alarms on viewer errors and `EvidenceDeleteFailed`.
  - CI: the `lambda-evidence-viewer.yml` workflow, the Lambda key lists in `_publish`, `_deploy-lambda`, `infra` and `oidc-negative`, and `ci-roles` permissions.
  - An ecs-service env deny-list for `LAMBDA_ENDPOINT` and `SQS_ENDPOINT`.
  - The IAM boundary needs consolidating first: it has about 17 characters of headroom left.
  - When byte deletion is first switched on, run the sweeper once with `EVIDENCE_DELETE_RETRY_DAYS=30`.

## Known gaps and risks
- **Accepted residual risk (owner, ADR-072).** A fully compromised disputes service can request links for any evidence pair. This is mitigated by the audit row, the viewer log and the cap. There are no CloudTrail S3 data events (owner ruling).
- **Retry-window limits.** Byte-delete failures older than 7 days, disputes erased before deletion is enabled, and backlogs over the batch size fall back to the 365-day lifecycle.
- **Purge query cost.** It scans `dispute_evidence` without an index. Add a partial index on `(updated_at) where status = 'ERASED'` if the table grows.
- **Local endpoint overrides.** `LAMBDA_ENDPOINT` and `SQS_ENDPOINT` are not yet rejected by the ecs-service module. This is listed in BO-10g.
- **UX.** After the download starts, the blank tab stays on `about:blank` in some browsers.
- **Two lists not updated.** `CLAUDE.md` (repo layout) and `.claude/agents/async-lambda.md` still list three Lambdas. Both are owner-maintained, so they were left unchanged.
